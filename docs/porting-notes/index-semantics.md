# Composite indexes: behavior of the Java Cloud Datastore emulator

How the Java emulator records queries, writes index files and enforces composite indexes. The index algorithm itself
(which index a query needs, and the "minimum" index) is the App Engine SDK's open-source `CompositeIndexManager` /
`IndexComponentsOnlyQuery` (GoogleCloudPlatform/appengine-java-standard, Apache-2.0); the emulator's file handling
behaves like that SDK's `LocalCompositeIndexManager` with the differences marked ★ below.

Evidence: the `tests/conformance/projects/index_*` cases (index files and NEED_INDEX errors recorded from Java byte for
byte) and black-box probes. Items marked UNVERIFIED were not confirmed by a probe; `docs/reference-behavior.md` records
what the project cases settled.

Differences from the App Engine SDK's local index manager, each marked ★ below:
1. `--index_file` support, which replaces the project directory's index file.
2. The YAML default path is `<appDir>/WEB-INF/index.yaml`. The SDK uses `<appDir>/index.yaml`.
3. `--regenerate_indexes`. Without it, generated indexes already in the file are carried over.
4. With `--require_indexes`, **every** query is verified, not only new ones.
5. Missing indexes fail with gRPC `FAILED_PRECONDITION` (§4.4).
6. The XML timestamp uses the system time zone.
7. XML output is written as UTF-8.

---

## 1. Configuration

### 1.1 Format and files
- The format is fixed for the life of the process: YAML when the project uses `index.yaml`, XML otherwise.
- With `--index_file`, that file is the index file and the project directory plays no part in index handling.
  Otherwise the index file is derived from the project directory (default `.`):

| format | index file | generated file |
|---|---|---|
| XML | `<appDir>/WEB-INF/datastore-indexes.xml` | `<appDir>/WEB-INF/appengine-generated/datastore-indexes-auto.xml` (the `appengine.generated.dir` system property overrides the directory) |
| YAML ★ | `<appDir>/WEB-INF/index.yaml` | the same file, below the `# AUTOGENERATED` marker |

- If `--index_file` names a missing file, the CLI creates it containing `indexes:\n# AUTOGENERATED\n`.
- **UNVERIFIED:** where XML mode with `--index_file` writes the generated file. Probe: start with `--index_file` naming
  an XML file outside any project directory, run a new query, and look for the generated file. The case is hard to
  reach anyway: the CLI's YAML stub is not valid XML (§5.6).

Black-box confirmation: `start --store_on_disk=false --consistency=1.0 /work/proj`, with an `index.yaml` present and no
XML, chose XML. A query `ORDER BY a ASC, b DESC` on K wrote `/work/proj/WEB-INF/appengine-generated/datastore-indexes-auto.xml`
containing `<!-- Indices written at Tue, 27 Oct 2026 08:16:36 UTC -->`, `Used 1 time in query history`, and `source="auto"`.

## 2. Query history

### 2.1 Which requests are recorded
Every `runQuery` that passes validation is recorded, after its results are computed but before they are returned (so a
NEED_INDEX failure returns no results):
- structured and GQL queries (GQL is converted to a structured query first; bound values end up in filter values);
- queries inside transactions (the transaction is not part of the history key);
- kindless and pseudo-kind queries (`__kind__`, `__property__`, `__namespace__`, `__entity_group__`). They almost never
  need a composite index (§6), but a new one still triggers a file write (§5);
- projection, keys-only, distinct, and paged queries. Each continuation page is a separate request with a different
  cursor, so it is a **new history entry** and triggers another file write.

Invalid queries, lookups, commits, aggregation queries (UNIMPLEMENTED in Java), and export/import never reach the history.
App Engine v3 `RunQuery` calls are recorded like v1 queries.

### 2.2 History key
The key is the query after the SDK's normalization (`NormalizedQuery`, then `IndexComponentsOnlyQuery`'s removal of
natively supported components):
1. Single-value `IN` becomes `EQUAL`. Duplicate EQUAL filters (same name *and* value) are dropped.
2. Orders are dropped if they repeat or match an EQUAL-filtered property (a property that also has an inequality filter
   keeps its order).
3. Redundant EXISTS filters are dropped. An EXISTS filter is added for every projection or distinct property that isn't
   already constrained.
4. All orders are dropped if there is a `__key__ ==` filter. Orders after a `__key__` order are dropped.
5. If no EXISTS filter is present, a trailing `__key__ ASC` order is removed, and if there is also no `__key__ DESC`
   order and no non-`__key__` inequality filter, **all `__key__` filters are removed**.

Two requests share a key only if everything else left in the query is equal: project, namespace, kind, ancestor,
filter values, orders, limit, offset, cursors, keys-only, projection and distinct properties. In practice almost every
distinct request is a new key. **UNVERIFIED:** whether every v1 field (e.g. `limit`) reaches the key; probe by running the
same composite query with different limits and watching the file timestamp and "Used N times".

Counting: the first execution of a key counts 1 ("Used 1 time"); repeats only increment the in-memory count. The file's
index list sums the counts of all history keys that need the same index, in the order the indexes were first seen.

## 3. `--regenerate_indexes` ★
It only matters when the file is rewritten. Nothing happens at startup. A rewrite writes:
1. the indexes needed by the query history, in first-seen order, minus those equal to a manual index;
2. unless `--regenerate_indexes` is set: the generated indexes already in the file that are not in (1), appended in file
   order with count 0 (`Used 0 times` in XML).

So by default generated indexes survive every rewrite; with `--regenerate_indexes` the generated section is replaced by
indexes from this run's history on the first write. A write error is logged (`Unable to write %s`) and ignored.

Caveat (XML): when the **manual** file (`datastore-indexes.xml` or `--index_file`) doesn't exist, the generated file is
not read either. So in XML mode without a manual file, old auto entries are always lost, whatever the flag says.

## 4. `--require_indexes`, verification, and errors

### 4.1 When queries are verified
There are two independent ways to get NEED_INDEX:
1. **`--require_indexes`**: every query execution is verified ★.
2. **Auto-generation disabled in the file**: XML `autoGenerate="false"`, or a YAML file that exists but has no
   `# AUTOGENERATED` line. Only the **first** execution of a history key is verified. Resending the *identical* request
   succeeds, because its key is no longer new.

**UNVERIFIED:** whether a query that fails `--require_indexes` (with auto-generation on) still ends up in the generated
file, and when. Probe: send a failing query, then a different new query, and check the file and whether the first query
passes before and after a restart (§4.2).

### 4.2 The set of known indexes
The indexes a query is checked against (manual and generated, from both files) are loaded the first time any
verification runs and are **never reloaded**: later edits to the files, the indexes the emulator writes itself, and
`/reset` don't change them.

A query passes if it needs no index, if its index is known, or if the known indexes can serve it together (the SDK's
`minimumCompositeIndexForQuery` returns null, §6.4).

### 4.3 Message text
- XML: `This query requires a composite index that is not defined. You must update <index file> or enable autoGenerate to
  have it automatically added.`
- YAML: `This query requires a composite index that is not defined. You must update <index file> or add "# AUTOGENERATED"
  to have it automatically added.`
- Only when the minimum index differs from the needed one (known indexes partly cover the query), the message continues
  with `\n\nThe minimum required index is:\n` and the index:
  - XML: `    <datastore-index kind="K" ancestor="false" source="manual">\n        <property name="a" direction="asc"/>\n    </datastore-index>\n\n`;
  - YAML: `- kind: "K"\n  properties:\n  - name: "a"\n  - name: "b"\n    direction: desc\n` (`direction` omitted for asc,
    `  ancestor: yes\n` only when true).
- **In the common case (no partial cover) the message is just the first sentence.**
- `<index file>` is the path as constructed: the `--index_file` value as given, or `<appDir>/WEB-INF/datastore-indexes.xml`
  / `<appDir>/WEB-INF/index.yaml` with `appDir` as passed on the CLI (default `.`).

### 4.4 Status
gRPC `FAILED_PRECONDITION`, with the description exactly equal to the message above: no prefix, and no "no matching index
found. recommended index is:" text. REST renders it as HTTP 400 with status `FAILED_PRECONDITION` (project cases). An
ad-hoc transaction begun for the query is rolled back.

## 5. File formats and when files are written

### 5.1 When
- **Never at startup and never on reset.** The one exception is the CLI writing a missing `--index_file` (§1.1).
- A write happens when **all** of these hold:
  - the query's history key is new (§2.2);
  - verification didn't fail first;
  - the file allows auto-generation (XML: no manual file, or `autoGenerate="true"`; YAML: no file, or the file has the
    marker);
  - `--store_index_configuration_on_disk` is not false.
- It writes **even when the new query needs no composite index**. For example, the first plain kind-only query creates
  `datastore-indexes-auto.xml` with the empty element.
- Every write is a complete rewrite of the generated section (§3). The file is re-read on every new query.
- XML counts on disk lag until the next new key arrives, because repeats only increment the in-memory count.

### 5.2 Index ordering in the output
1. Indexes from history, in first-seen order of the history keys.
2. Indexes equal to a manual index are removed.
3. Unless `--regenerate_indexes` is set, generated indexes from the file that aren't already present are appended, in
   file order, with count 0.

### 5.3 XML
The target is the generated file (§1.1); its parent directories are created. The output is:
```
<!-- Indices written at {TS} -->\n
\n
```
then, if there are no indexes:
```
<datastore-indexes autoGenerate="true"/>\n
\n
```
otherwise:
```
<datastore-indexes autoGenerate="true">\n
\n
    <!-- Used {N} time{N==1?"":"s"} in query history -->\n      (repeated per index)
{index}
</datastore-indexes>\n
```
Each `{index}`:
- No properties: `    <datastore-index kind="{K}" ancestor="{true|false}" source="auto"/>\n\n`
- With properties: `    <datastore-index kind="{K}" ancestor="{bool}" source="auto">\n` + per property
  `        <property name="{P}" {ATTR}/>\n` + `    </datastore-index>\n\n`.
  - ATTR is `direction="asc"`, `direction="desc"`, `mode="geospatial"`, or `""` (which gives `name="x" />`).
  - For a geospatial index the ancestor attribute is replaced by `""`, which gives `kind="K"  source="auto"` with two
    spaces.
  - Generated non-geo properties always carry a direction (§6.3).
- No XML escaping is applied to kind or property names. A kind containing `"` or `<` produces invalid XML.

`{TS}` is the format `EEE, d MMM yyyy HH:mm:ss z` in the system time zone ★, e.g. `Tue, 27 Oct 2026 08:16:36 UTC`. The day of
month isn't zero-padded, and the zone is the short name (e.g. `UTC`, `IST`, `PST`).

Reading XML:
- If the manual file is missing, there are no indexes and auto-generation is on.
- Otherwise the root's `autoGenerate` must be exactly `"true"` or `"false"`, or the query fails with
  `autoGenerate=true|false is required in datastore-indexes.xml`.
- Then the generated file is read if it exists.
- In **both** files, each `<datastore-index>` is classified by its `source` attribute: absent or `manual` → manual;
  `auto` → generated. Any other value is an error.
- `kind` and property `name` are trimmed. `ancestor` is true only for `true` (case-insensitive), default false.
  `direction` is set only if present (`asc`/`desc`, otherwise `Unrecognized direction: x`); `mode` only if present
  (`geospatial`).

With `autoGenerate="false"`, nothing is written, and queries are verified (§4.1) against manual and `source="auto"`
entries from both files.

### 5.4 YAML (a single file)
The first line whose trimmed text is `# AUTOGENERATED` starts the generated part; that line and everything after it are
"generated", everything before is "manual". Lines are re-emitted with `\n`, so CRLF becomes LF and the trailing newline is
normalized.

Reading: no file → no indexes, auto-generation on. Otherwise auto-generation is on iff the marker was seen; the manual part
and (after the marker) the generated part are parsed as `indexes:` lists. A missing direction means ascending. An I/O
error fails the query with `Received IOException parsing the input stream.`

Writing: the manual part is the existing text above the marker, or `indexes:\n\n` if the file doesn't exist. Then:
```
{manualPart}# AUTOGENERATED\n
\n
# This index.yaml is automatically updated whenever the Cloud Datastore\n
# emulator detects that a new type of query is run. If you want to manage the\n
# index.yaml file manually, remove the "# AUTOGENERATED" marker line above.\n
# If you want to manage some indexes manually, move them above the marker line.\n
\n
{generated}
```
- `{generated}` lists the indexes in map order, each line followed by `\n`:
  - `- kind: "{K}"\n`
  - `  ancestor: yes\n` only if ancestor is true
  - `  properties:\n` only if there are properties
  - per property: `  - name: "{P}"\n`, then `    direction: desc\n` only when descending, then `    mode: geospatial\n`
    if the mode is set
- No counts and no timestamp are written in YAML.
- No quoting or escaping of `"` in names.
- The file is written in UTF-8, creating parent directories.

### 5.5 `--store_index_configuration_on_disk=false`
- History is still kept in memory, and the file is still **read** on every new key.
- If the file disables auto-generation, verification still runs; `--require_indexes` still works.
- The only change: nothing is ever written.
- The in-memory history is visible only through the App Engine v3 `GetIndices` call.

### 5.6 Malformed files
**UNVERIFIED:** how malformed XML and YAML index files fail. Probe: start with a malformed file (and, separately, an
XML-mode `--index_file` that the CLI pre-filled with the YAML stub) and run a query.

## 6. Which index a query needs
This is the SDK's open-source `CompositeIndexManager.compositeIndexForQuery` / `minimumCompositeIndexForQuery` and
`IndexComponentsOnlyQuery`, unchanged in the emulator. Summary for a port:

### 6.1 Components (after §2.2 normalization)
- EQUAL filters → `prefix` (in filter order); EXISTS → `exists`; `< <= > >=` → `ineq`; CONTAINED_IN_REGION → geo. A filter
  on `__key__` sets `hasKeyProperty`.
- If there are no orders and `ineq` is non-empty, the inequality property becomes an order **with no direction**.
- `groupBy` = the distinct properties; `exists -= groupBy`.
- For each order: `__key__` sets `hasKeyProperty`; the property leaves `groupBy`; it is appended to the ordered properties.
- `postfix = [Ordered(orderProps), Unordered(groupBy), Unordered(exists)]`. Unordered sets are sorted by UTF-16 code-unit
  order.

### 6.2 compositeIndexForQuery → Index or none
```
if no filters && no orders                       -> none        (counts filters/orders after normalization)
props = geo ? sorted(prefix, no mode) ++ sorted(geo, mode=GEOSPATIAL)
            : sorted(set(prefix)), ASC
              ++ orderProps (missing direction → ASC)
              ++ sorted(groupBy), ASC
              ++ sorted(exists), ASC
if hasKind && prefix nonEmpty && prefix.size == filters.size && !hasKeyProperty && orders empty -> none
if hasKind && !ancestor && props.size <= 1 && !geo && (!hasKeyProperty || props[0].direction == ASC) -> none
return Index{kind, ancestor, props}
```
- Kindless queries in practice need no index: the only filters and orders they allow are on `__key__`, and those are
  removed by normalization.
- Pseudo-kind queries count as having a kind, so the rules apply normally. E.g. `__property__` with an ancestor and no
  filters → none.
- **Ancestor plus equality-only** → none. Ancestor plus any order or inequality → an index with `ancestor="true"`.
- Projection: the EXISTS filters added for projected properties block the `__key__` removal, and 2 or more projected
  properties → an index like `K: p1 ASC, p2 ASC` (sorted). Distinct works the same way.
- Keys-only, limit, offset, and cursors don't affect the needed index (they do affect the history key).

### 6.3 Index identity
- Generated properties always have a direction (ASC or DESC) and no mode, except geo properties: mode GEOSPATIAL and no
  direction.
- YAML-parsed properties always have a direction (missing → ASC), so they compare equal to generated ones.
- XML-parsed properties without a `direction` attribute have no direction, so they are **not equal** to the generated
  ASC property:
  1. the query still passes verification, because a missing direction matches either direction when known indexes are
     combined (§4.2);
  2. the same index is also written into `datastore-indexes-auto.xml`, since it doesn't equal the manual one.

  A port that canonicalizes "missing direction = ASC" differs only in that duplicate. **UNVERIFIED.**
- `ancestor` always takes part in the comparison.

### 6.4 minimumCompositeIndexForQuery
- No needed index → none. Geo → the needed index.
- For each known index of the same kind (skipped if the index has an ancestor and the query doesn't): match the postfix
  components from the end. Ordered components need an exact or direction-wildcard match; unordered ones a set match. The
  index's remaining properties must be a subset of the query's equality properties.
- Indexes are grouped by postfix, accumulating which equality properties and ancestor they cover. If one group covers
  everything → none (the known indexes can serve the query together).
- Otherwise, if nothing matched → the needed index. Else the group with minimum `cost = |remaining eq| + (remaining
  ancestor ? 2 : 0)` gives `Index{kind, ancestor=remainingAncestor, props = remaining eq names sorted ASC ++ that postfix}`.
  Ties are broken in an implementation-defined order.
- Only used for the error text (§4.3).

Not handled: `IN` with more than one value is rejected earlier ("Unsupported filter operator"). `NOT_EQUAL`/`NOT_IN` and
multiple inequality properties are rejected by the emulator's validation before reaching the index manager.

## 7. Reset and lifecycle
- `POST /reset`:
  - When **storing on disk** (default), it logs `Cannot reset a Datastore Emulator when it is storing data on disk...` and
    fails. Nothing is reset, and history is kept.
  - With `--store_on_disk=false`: data, id counters and **query history** are cleared.
- **Not reset:** the set of known indexes used for verification (§4.2), the format, the flags, and the index files.
  - After a reset, the next new key rewrites the generated section from post-reset history only, plus carried-over file
    entries unless `--regenerate_indexes` is set.
  - In XML mode without a manual file, old auto entries are dropped (§3).
- History is **global to the process** and isn't split by project, database, or namespace. One index file serves all
  projects. Equal indexes from different projects (same kind and properties) merge, and their counts add up.
