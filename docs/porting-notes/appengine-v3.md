# App Engine v3 API server (`apphosting.tools.devappserver2.CallHandler`)

Observed behavior of the Java emulator's App Engine v3 API server, from black-box probes against a real Java emulator
(`tools/javaemu.sh start --testing`, plus one `--require_indexes` run). Items marked **UNVERIFIED** were not confirmed
with a probe.

The probes became the conformance scenarios `tests/conformance/scenarios/v3_*.scn` (generated by
`tools/scenario-gen/v3.py`, recorded with `tools/record-v3.sh`) and the project cases
`tests/conformance/projects/v3_*.case`; `crates/oxide-server/tests/appengine.rs` covers task delivery.
What datastore-oxide implements, and where it still differs, is in `docs/reference-behavior.md`.

---

## 0. Overview

The CallHandler service is served on the same port as v1. It dispatches on `request.method` **only** and parses
`request.request` as that method's v3 message. App ids in requests are mapped to project ids (§3), the call runs
against **the same data and engine as the v1 API**, and project ids in responses are mapped back to app ids. So the v3
API behaves like the shared engine **without the v1 layer's validation and response shaping**: only the engine's own
checks apply (§4).

---

## 1. The CallHandler envelope

Service `apphosting.tools.devappserver2.CallHandler`, unary method `HandleCall(Request) returns (Response)`.
The file is `syntax = "proto3"`, so fields equal to their defaults are not serialized.

```
Request  { string service_name = 2; string method = 3; bytes request = 4; string request_id = 5;
           string txn_add_task_callback_hostport = 6; }
Response { bytes response = 1; bytes exception = 2; ApplicationError application_error = 3;
           bytes java_exception = 4; RpcError rpc_error = 5; }
ApplicationError { int32 code = 1; string detail = 2; }
RpcError { int32 code = 1; string detail = 2; enum ErrorCode { UNKNOWN=0 CALL_NOT_FOUND=1 PARSE_ERROR=2 ... } }
```

### 1.1 Which request fields matter

| Field | Use |
|---|---|
| `method` | Selects the handler. Exact, case-sensitive string match |
| `request` | Parsed as the method's request message (§2) |
| `txn_add_task_callback_hostport` | Read **only** by `Commit`; see §4.11 |
| `service_name` | **Ignored.** Probe: `Get` with service `datastore_v3`, `""`, `taskqueue`, `memcache` or `xyz` all perform a datastore Get |
| `request_id` | **Ignored**, and not echoed in the response |

### 1.2 Outcomes

| Case | Wire result |
|---|---|
| Success | `Response{response = serialized method response}`. For an empty message (Rollback/AddActions, an empty `GetResponse`/`PutResponse`/`DeleteResponse`/`CompositeIndices`), `response` is empty and **the envelope is 0 bytes** |
| The request bytes fail to parse | `Response{rpc_error{code: 2 (PARSE_ERROR), detail}}` (§1.3) |
| A datastore error | `Response{application_error{code: <datastore_v3 Error.ErrorCode>, detail}}` |
| An unexpected failure | No `Response`: the call ends with **gRPC status UNKNOWN and an empty description**. Probe-confirmed triggers are listed in §1.4 |

`exception` and `java_exception` are never set. A code-less `application_error` (code 0) may occur for index
configuration errors; **UNVERIFIED**, no probe hit it.

### 1.3 Exact error texts at the envelope level

- Unknown method:
  `application_error{code: 1, detail: "Cannot find definition for method: <method>"}`. The code is BAD_REQUEST.
  Probe: `get`, `Touch`, `DeleteCursor`, `CreateIndex`, `UpdateIndex`, `DeleteIndex`, `Add`, `BulkAdd` and `""`
  each give this, with the method echoed verbatim (empty for `""`).
- v3 request parse failure: `rpc_error{code: 2, detail: "Error parsing protocol message"}`. Probe triggers: a
  truncated length, a truncated varint, an unmatched start/end group, wire types 6/7 and tag 0.
- A missing `required` field anywhere in the parsed v3 message, recursively: `rpc_error{code: 2, detail:
  "Message was missing required fields.  (Lite runtime could not determine which fields were missing)."}`
  (two spaces after `fields.`). The `required` fields are those of the v3 messages: `Transaction.handle/app`, `Query.app`, `Query.Filter.op`, `Query.Order.property`,
  `NextRequest.cursor`, `Cursor.cursor`, `BeginTransactionRequest.app`, `GetIndicesRequest.app_id`,
  `Reference.app/path`, `Path.Element.type`, `EntityProto.key/entity_group`, `Property.name/value/multiple`, the
  required fields of `UserValue`/`PointValue`/`ReferenceValue`/`CompositeIndex`/`Index`, and so on. Probes: an empty
  `Commit`, `Rollback`, `BeginTransaction`, `RunQuery`, `Next` or `GetIndices`; a key without `app` or `path`; an
  element without `type`; an entity without `entity_group`; a property without `multiple` or `value`. All give this
  error. An empty `Get`, `Put`, `Delete`, `AllocateIds` or `AddActions` request is valid.
- **Lenient parsing**: unknown fields are skipped. So is a *known* field number sent with the wrong wire type.
  Probe: `Get` with bytes `0d 00000000` (field 1 as fixed32) or `08 01` (field 1 as varint) succeeds as an empty
  Get.
- `AddActions` errors use protobuf-java's standard texts:
  - a truncated message gives `rpc_error{code: 2, detail: "While parsing a protocol message, the input ended
    unexpectedly in the middle of a field.  This could mean either that the input has been truncated or that an
    embedded message misreported its own length."}`;
  - a missing required field (`queue_name`/`task_name`/`eta_usec`) gives gRPC **UNKNOWN**, and so does every later
    such request; valid AddActions calls still work.

### 1.4 Probe-confirmed gRPC UNKNOWN triggers

| Request |
|---|
| `RunQuery` with `app: ""`; `Put` whose first key has `app: ""` |
| An app id that is still invalid after scrubbing, e.g. `s~Example.com:Foo` (§3.2) |
| `Put` of a key whose non-final element is incomplete (`P:<none>/K:a`) |
| `Put` of an indexed `ENTITY_PROTO` property whose bytes are not an EntityProto |
| `RunQuery` with operator `NOT_EQUAL` (9) / `NOT_IN` (10) |
| `RunQuery`/`Next` with `count < 0`; `RunQuery` with `limit < 0` |
| `Next` whose `cursor.app` names a project that has never been used (or `app` unset) |
| `AddActions` whose transaction's project has never been used (no transaction, an unknown app, or `datastore_transaction` bytes, which are not app-converted) |
| `Commit` with actions and an unreachable `txn_add_task_callback_hostport` (raised **after** the commit was applied) |

## 2. Supported methods

The service name plays no part (§1.1).

| method | request parsed as | response |
|---|---|---|
| `Get` | `GetRequest` | `GetResponse` |
| `Put` | `PutRequest` | `PutResponse` |
| `Delete` | `DeleteRequest` | `DeleteResponse` |
| `RunQuery` | `Query` | `QueryResult` |
| `Next` | `NextRequest` | `QueryResult` |
| `BeginTransaction` | `BeginTransactionRequest` | `Transaction` |
| `Commit` | `Transaction` | `CommitResponse` |
| `Rollback` | `Transaction` | empty |
| `AllocateIds` | `AllocateIdsRequest` | `AllocateIdsResponse` |
| `GetIndices` | `GetIndicesRequest` | `CompositeIndices` |
| `AddActions` | **`taskqueue.TaskQueueBulkAddRequest`**, not `AddActionsRequest` | empty |

Not supported, so they get `Cannot find definition for method: X`: `Touch`, `DeleteCursor`, `CreateIndex`,
`UpdateIndex`, `DeleteIndex`, plus any taskqueue/memcache/etc. method name (`Add`, `BulkAdd`, …). Other services are
not emulated. A taskqueue/memcache call that happens to use a datastore method name (`Get`, `Put`, …) is **executed as
a datastore call**, because `service_name` is never checked. The emulator also acts as a CallHandler *client*: on
Commit it sends transactional tasks to `taskqueue`/`Add` at `txn_add_task_callback_hostport` (§4.11).

## 3. App ids ↔ project ids

### 3.1 The mapping

- Request direction: each app id is mapped to a project id (§3.2), and the emulator remembers that app id for that
  project. So the **last** app id that mapped to a project wins (`s~p`, `e~p`, `dev~p` and `p` all map to `p`).
- Response direction: a project id is mapped back to the app id last remembered for it. If there is none, a WARNING
  `Attempting to convert a stored project ID to an application ID failed. The application ID of returned entities
  may have changed.` is logged and the project id is returned unchanged. The database id plays no part.
- The memory is process-global: it is **not cleared by `/reset`** (probe: `e~p7` registered before a reset still shows
  up after it) and not persisted. Because every request registers its own app id first, the app id in a response is
  usually the one from the request. Ids that never appeared in a v3 request come back bare: a reference value written
  via v1 to project `p6` is returned as `app: "p6"`.

### 3.2 App id → project id

- `""` stays `""`, so later steps fail (§3.5).
- A **valid** app id is `[partition~]project`, where `partition` (before the first `~`) is 1-100 characters of
  `[a-z0-9-]`, and something must follow the `~`. The project id is the rest, and it is valid when:
  - it is `[domain:]name`: the domain is at most 100 characters, starts with `[a-z0-9]` and continues with
    `[a-z0-9.-]`; the name is at most 100 characters, starts with `[a-z0-9]` and continues with `[a-z0-9-]`; an empty
    name and a trailing `-` are allowed;
  - or it is wrapped in `__…__` (at least 4 characters), with the same rules inside (e.g. `s~__x__`);
  - a metadata project `__metadata-<digits>_<project>__` maps to `<project>`.
- An **invalid** app id is scrubbed, and a WARNING `Provided application id '%s' is invalid for storage in Cloud
  Datastore Emulator. Using '%s' instead.` is logged. Scrubbing takes the part after the first `~` (if any); if it
  contains `:`, it becomes `<domain>:scrubbed-<name>` with characters outside `[a-z0-9.-]` (domain, at most 100) or
  `[a-z0-9-]` (name, at most 91) replaced by `-`; otherwise `scrubbed-<rest>` with characters outside `[a-z0-9-]`
  replaced by `-`, at most 91 of them (91 = 100 - `len("scrubbed-")`).
- If the scrubbed id is still invalid, the call fails with gRPC UNKNOWN.

The examples below are probe-confirmed; the scrubbed project id is read from the Java log:

| app id in request | project id | response app id |
|---|---|---|
| `s~p`, `e~p`, `dev~p`, `p` | `p` | as sent (the last one used) |
| `example.com:foo`, `s~example.com:foo` | `example.com:foo` | as sent |
| `__metadata-12_p__` | `p` | as sent |
| `s~__x__` | `__x__` | as sent |
| `S~Foo` | `scrubbed--oo` | `S~Foo` |
| `a~b~c` | `scrubbed-b-c` | `a~b~c` |
| `~p`, `aaa…(101)~p` | `scrubbed-p` | as sent |
| `-p`, `s~-p` | `scrubbed--p` | as sent |
| `s~p_q` | `scrubbed-p-q` | as sent |
| `s~p3#db` | `scrubbed-p3-db` | as sent |
| `s~` | `scrubbed-` | `s~` |
| `x`×101 | `scrubbed-` + `x`×91 | as sent |
| `s~Example.com:Foo` | — | gRPC UNKNOWN |
| `""` | `""` | Get: `Reference must set app` error; Put/RunQuery: UNKNOWN (§3.5) |

### 3.3 Fields rewritten on the way in

- `GetRequest`: `key[]` (Reference.app), `transaction.app`, and each `transaction.composite_index[].app_id`.
- `PutRequest`: `transaction` (as above), `composite_index[].app_id`, and `entity[]`: `key.app`, plus each `property`/`raw_property`
  whose value is a `ReferenceValue` with `app`, plus each `ENTITY_PROTO`-meaning string value (parsed as an
  EntityProto, converted recursively and re-serialized; a parse failure logs `Received an entity value which could not
  be parsed.` and leaves the value as is). `entity_group` and `owner` are not touched.
- `DeleteRequest`: `key[]`, `transaction`, `composite_index[]`.
- `Query`: `app`, `transaction`, `ancestor`, each `filter[].property[]` (reference / ENTITY_PROTO values), and
  `composite_index[]`. **Not** `compiled_cursor` / `end_compiled_cursor`.
- `NextRequest`: `cursor.app`.
- `BeginTransactionRequest.app`. **Not** `previous_transaction.app` (the project comes from `app`).
- `Transaction` (Commit/Rollback): `app` and `composite_index[]`.
- `AllocateIdsRequest`: `model_key`, `reserve[]`.
- `GetIndicesRequest.app_id` (only the string is passed on; `database_id` is dropped).
- `TaskQueueBulkAddRequest`: each `add_request.app_id` and `add_request.transaction.app` (a proto2 Transaction).
  **Not** `datastore_transaction` (bytes).

### 3.4 Fields rewritten on the way out

- `GetResponse`: `entity[].key`, `entity[].entity` (as for Put), and `deferred[]`.
- `PutResponse.key[]`.
- `QueryResult`: `cursor.app`, `result[]` (as for Put), and `index[].app_id`. **Not** `compiled_cursor`,
  `result_compiled_cursor`, `skipped_results_compiled_cursor` or `compiled_query`: these carry **bare project ids**.
  Probe: `compiled_cursor { postfix_position { key { app: "pqr" … } } }` and
  `compiled_query { primaryscan { index_name: "\n\003pqr\032\001K…" } }` for app `s~pqr`.
- `Transaction.app` (BeginTransaction).
- `CommitResponse.version[].root_entity_key`.
- `CompositeIndices.index[].app_id`.
- `AllocateIdsResponse` and `DeleteResponse` are unchanged (no app ids).
- `TaskQueueAddRequest.app_id` / `transaction.app` are rewritten before the callback is sent.

Compiled cursors sent back in a Query are not rewritten either, so a cursor key must carry the project id. Probe: a
cursor whose key app is `pz` works for app `s~pz`. With key app `s~pz` or `zzz` the query **silently returns nothing**
(`more_results: false`); there is no error.

### 3.5 Empty / invalid app ids

The empty string passes through the resolver unchanged. Then:

- a Get key with `app: ""` → BAD_REQUEST `A OnestoreEntity.Reference must set app.`;
- `Put`/`RunQuery` → gRPC UNKNOWN;
- `GetIndices` with `app_id: ""` → succeeds, and every returned index has `app_id: ""`.

### 3.6 v1 ↔ v3 sharing (probe-confirmed)

They share **everything**: the same data keyed by project id, one version/commit-timestamp counter per
project, one sequential id counter, one transaction handle counter, the query-cursor counter (§4.6), the global query
history and index file, and persistence/export.

- A v3 `Put` with `s~p3` is seen by v1 `lookup` in project `p3`, and a v1 insert in `p4` is seen by v3 with `s~p4`,
  `e~p4`, `dev~p4` or `p4`, each echoed back as sent.
- Transaction handles are interchangeable. The v1 transaction bytes are `0x11 + LE fixed64 handle` (field 2, *not*
  a v3 `Transaction` proto). A v3 `Transaction{handle: h, app: "s~p"}` can commit a v1 transaction, and v1 can commit
  `0x11+LE(h)` of a v3 transaction (probe `p15.py`).
- Key, entity group and database semantics are identical. v3 `Reference.database_id` is the v1 database id: it is
  stored per key, and the app-id mapping ignores it.
- What each side sees of the other's data (probe `p13_interop.py`):
  - **v3 view of v1 data** is exactly the "user-visible" v3 `EntityProto` that `crates/oxide-api/src/v3.rs` already
    encodes for exports. Examples: GD_WHEN micros, BYTESTRING/BLOB, GEORSS_POINT, `multiple: true` per array element,
    EMPTY_LIST, ENTITY_PROTO bytes (whose nested key app is rewritten to the request's app id), excluded values in
    `raw_property`, and `entity_group` = root. Property order is the v1 request order.
  - **v1 view of v3-only constructs**: meanings 1-13/17 keep their `meaning` number on a string/integer value;
    BYTESTRING (16) → `blobValue`; a point without a meaning → `geoPointValue` + `meaning: 23`; a `UserValue` → an
    `entityValue` {email, auth_domain, user_id} with `meaning: 20`; a single value with `multiple: true` → a
    one-element array; a `PropertyValue` with two fields set (int + string) → the integer only; `owner`/`kind`/
    `kind_uri`/`meaning_uri` are invisible to v1.

## 4. Methods

General rules for all methods:

- Requests are not checked for consistent apps. The **project** is chosen as follows:
  - Get: per key; the transaction is looked up in the first key's project;
  - Put: the **first entity's** app;
  - Delete: the **first key's** app;
  - RunQuery: `Query.app`;
  - Next: `cursor.app`;
  - BeginTransaction/Commit/Rollback: `Transaction.app`;
  - AddActions: `add_request[0]`'s transaction app.
- **Quirk, probe-confirmed (`p6_put2.py`)**: a Put of `[s~pq/K:d, s~other2/K:d]` writes both into project `pq`.
  The second overwrites the first, and both returned keys say `s~pq`; `s~other2` stays empty. Delete behaves the same.
- Versions are the per-project commit timestamps of the v1 engine. Missing entities report the current timestamp.

### 4.1 Get (`GetRequest` → `GetResponse`)

Fields:

- `key[]`.
- `transaction`: only `handle` is used, looked up in the first key's project.
  An unknown handle gives `transaction has expired or is invalid`.
- `strong`: a Get is strong unless it has no transaction and sets `strong: false` explicitly; only
  that case gives an eventual read.
- `allow_deferred` is passed through but has no effect: no `deferred` keys are ever returned (probe).
- `read_time_epoch_micros` is ignored.
- `failover_ms` is ignored.

Validation (probe `p4_get.py`). Every error is code 1 BAD_REQUEST:

| Input | detail |
|---|---|
| `app: ""` | `A OnestoreEntity.Reference must set app.` |
| empty path | `A OnestoreEntity.Path must have at least one Element.` |
| incomplete element (no id/name, or `id: 0`) | `Incomplete key.path.element: type: "K"\n`: the element in protobuf debug text. With `id: 0` the output is also just `type: "K"\n` (probe) |
| id and name both set | `A OnestoreEntity.Path.Element must not set both id and name.` |
| `name: ""` | `When OnestoreEntity.Path.Element has name set it must not be empty.` |
| `name_space: ""` explicitly set | `The namespace is the empty string.` |

**Not** validated on reads, unlike v1: empty or reserved kinds (`""`, `__foo__`), reserved names, invalid/reserved
namespaces (`a b`, `__x__`), invalid database ids, kind/name longer than 1500 bytes, more than 100 path elements,
negative ids, duplicate keys. All of these simply come back missing.

Response, one `entity` per key in request order (`in_order` and `read_time_epoch_micros` unset):

- found: `Entity{entity: <EntityProto>, version: <entity version>}`;
- missing, strong read: `Entity{key, version: <current commit timestamp>}` (field order on the wire: version(3)
  before key(4));
- missing, eventual read (`strong: false`): `Entity{key}` with no version;
- found, eventual read: `entity` + `version`.

The entity is post-processed: `__scatter__` and other special properties are removed, computed properties are removed
and stashed ones restored (§4.2), and app ids are rewritten.

In a transaction it behaves like a v1 lookup: the same group tracking, snapshot and conflict rules
(`docs/porting-notes/txn-semantics.md`). **Plus**, when the transaction was begun without `allow_multiple_eg`,
touching a second entity group fails with BAD_REQUEST:

```
cross-group transaction need to be explicitly specified, see TransactionOptions.Builder.withXGfound both Element {\n  type: "K"\n  name: "a"\n}\n and Element {\n  type: "K"\n  name: "b"\n}\n
```

There is no space before `found`. Each element is printed in protobuf debug text format with 2-space indentation; the first is
the group already tracked, the second is the new one. With `allow_multiple_eg`, the 26th group fails with `operating on
too many entity groups in a single transaction.` (Datastore mode). v1 always begins transactions as XG.

### 4.2 Put (`PutRequest` → `PutResponse`)

Fields:

- `entity[]`.
- `transaction`.
- `composite_index[]`, `trusted`, `force`, `mark_changes`, `snapshot[]`, `auto_id_policy` and `sequence_number` are
  **all ignored**. Probe: setting them all changes nothing, and `auto_id_policy: SEQUENTIAL` still draws from the
  shared sequential counter.

Processing:

- **Auto ids**: an incomplete *last* element takes the next id from the global sequential counter, shared with v1
  commits and with v3 `AllocateIds` (§4.9). An incomplete *non-last* element gives gRPC UNKNOWN (§1.4).
- **`entity_group`**: kept **as sent** if it has elements. Probe: an entity sent with group `K:zzz` is returned with
  `entity_group {K:zzz}`. If it is empty, it is recomputed as the root element. Conflicts and versions use the real
  key root, not this field (inference; UNVERIFIED by a conflict probe).
- **Validation** (BAD_REQUEST):
  - `illegal property.name: __x__`, for any `^__.*__$` property name, in `property` or `raw_property`;
  - `The key path element name is longer than 1500 bytes.`;
  - `string property <name> is too long.  It cannot exceed 1500 bytes.` (two spaces), for an indexed string longer
    than 1500 bytes;
  - `Cannot modify entities in a read-only transaction.`;
  - transaction errors as in §4.1, including the XG message.
- **Accepted** (unlike v1): reserved kinds (`__foo__`), reserved names (`__a__`), an empty kind, an empty name,
  kinds longer than 1500 bytes, reserved or invalid namespaces, explicit `name_space: ""`, invalid database ids,
  property names that are empty or dotted, TEXT/BLOB meanings in `property` (index writes are counted for BLOB, not for
  TEXT), meaning `INDEX_VALUE`, and raw strings of 1048488+ bytes. A raw string of 1,048,488 bytes was accepted; Java has
  size limits (`Property %s is too long. It cannot exceed 1048487 bytes.`), but **UNVERIFIED** which input triggers them.
- **Storage is the v3 EntityProto, verbatim** apart from the steps listed here. Everything round-trips through a v3
  Get: `owner`, `kind`, `kind_uri`, `meaning_uri`, any meaning number, `multiple` flags (including several
  `multiple: false` values with the same name, and a single value with `multiple: true`), the split between
  `property` and `raw_property` (including the same name in both), property order, a `PropertyValue` with several
  fields set, `UserValue`, and a `PointValue` without a meaning.
- **Special properties** (the App Engine SDK's `EntityStorageConversions`, described in
  `docs/porting-notes/query-semantics.md` §embedded entities):
  - a client property with `computed: true` is stored and counted in the index writes, but **removed on every read**;
  - a client property with `stashed: N` is moved so that on read it sits at index N (appended if out of range; probe: `stashed: 3` on the first of 2 properties moves it to the end);
  - `__scatter__` is added to about half of the keys. It is never returned, but it can
    be used in orders and filters (probe: `order __scatter__` returns a permuted key order).

Response:

- non-transactional: `key[]` (complete, app rewritten), `cost{index_writes, entity_writes}` (the App Engine write
  cost, the same numbers as v1 `indexUpdates`), and `version[]`, one per entity in request order (the mutation's
  commit timestamp; puts of different groups get successive timestamps). Duplicate keys in one request get the same
  version (the last write wins).
- transactional: `key[]` and an **empty `cost {}`** (serialized as `12 00`), no versions; the write is buffered until
  Commit.
- empty `entity[]`: an empty response (0 bytes).
- Oddity (probe, not explained): a new entity with two `multiple: false` values named `x` returned `cost {0, 0}` and
  appeared to consume two timestamps. **UNVERIFIED** why; rare input.

### 4.3 Delete (`DeleteRequest` → `DeleteResponse`)

- Fields: `key[]` and `transaction`. `composite_index`, `trusted`, `force`, `mark_changes`, `snapshot` and
  `sequence_number` are ignored.
- Validation: an incomplete key gives `Incomplete key.path.element: type: "K"\n`. Reserved kinds are accepted (no
  error).
- Non-transactional response: `cost` + `version[]`, one per key, **including missing keys**, each of which consumes a
  commit timestamp. Probe: deleting an existing key and a missing one gave `cost{index_writes:3 entity_writes:1}
  version: 4 version: 5`; deleting nothing gave `cost{0,0}` plus a version.
- Transactional response: `cost {}` only.
- Empty `key[]`: an empty response.
- Same engine path as a v1 delete mutation.

### 4.4 RunQuery (`Query` → `QueryResult`)

This is the same query engine as v1. Matching, ordering, projections, cursors, pseudo-kinds, composite-index
bookkeeping and eventual consistency are covered by `docs/porting-notes/query-semantics.md` and
`index-semantics.md`. The v3 surface:

- **Used**: `app`, `name_space`, `kind`, `ancestor`, `filter[]`, `order[]`, `count`, `offset`, `limit`,
  `compiled_cursor`, `end_compiled_cursor`, `keys_only`, `transaction`, `property_name[]` (projection),
  `group_by_property_name[]` (distinct), `compile`, `search_query` (rejected).
  `database_id` is ignored, because queries are database-blind as in v1.
- **Ignored** (probe: no effect, no error): `composite_index`, `failover_ms`, `strong`, `hint`,
  `require_perfect_plan`, `min_safe_time_seconds`, `safe_replica_name`, `read_time_us`, `read_time_epoch_micros`,
  `shallow`, `persist_offset`, and **`distinct`**. With `distinct: true` alone the query is not distinct;
  `group_by_property_name` is what makes it distinct.
- **Batching**:
  - the batch size is `count` if set, else 20;
  - at most 300 results and at most 300 skipped results per batch;
  - `limit` caps the total (applied when the result snapshot is taken);
  - `offset` skips results; `skipped_results` is present **only when the offset is > 0**;
  - an offset left over beyond 300 carries into Next.
- **`more_results`** = the snapshot still has entries. It is `false` on the last batch, unlike v1's
  `MORE_RESULTS_AFTER_LIMIT` rule. When `true`, a query handle is registered and returned as `cursor{cursor: <handle>,
  app}`. Handles come from one counter, starting at 0, that **survives `/reset`**.
- **Response fields**:
  - `keys_only` = the query flag;
  - `index_only` = projection present;
  - `version[]`: one per full-entity result; none for keys-only or projection results;
  - `index[]` = the composite index the query needs (`app_id` rewritten, `id: 0`,
    `state: READ_WRITE`), even when nothing requires indexes. Probe: `x = 1 order y` → index `K(x, y)`;
    `order __key__ desc` → index `K(__key__ desc)`;
  - `small_ops` and `read_time_epoch_micros` are never set.
- **Result shapes**:
  - full entities, post-processed as in Get;
  - keys-only: `EntityProto{key, entity_group {}}`, an **empty group**;
  - projection: `EntityProto{key, property[] with meaning INDEX_VALUE (18), entity_group {}}`, one row per value
    combination.
- **`compile: true`** adds:
  - `compiled_query` (`primaryscan.index_name` = serialized index key text, `keys_only`);
  - `compiled_cursor{postfix_position{key, before: false, before_ascending}}` after the last result;
  - one `result_compiled_cursor` per result;
  - `skipped_results_compiled_cursor` when the offset is > 0.

  All of these carry bare project ids (§3.4). The cursor bytes are the v3 CompiledCursor that
  `oxide-engine/src/cursor.rs` already produces.
- **Errors** (probe `p7_query.py`, `p8_next.py`, `p14.py`); BAD_REQUEST unless stated:
  - `Only one inequality filter per query is supported.  Encountered both x and y` (two spaces);
  - `Filter has 2 properties, expected 1` / `Filter has 0 properties, expected 1` (IN with one value works; there is
    no multi-value IN);
  - `NOT_EQUAL`/`NOT_IN` → gRPC UNKNOWN; `EXISTS` (7) is accepted and acts as no filter (probe: returned all);
  - `full-text search unsupported` (any `search_query`);
  - `kind is required for non-__key__ filters`, `kind is required for all orders except __key__ ascending`;
  - `queries not supported on __entity_group__`;
  - `__key__ filter value must be a Key` (e.g. `property_name: ["__key__"]`);
  - `projection and keys_only cannot both be set`;
  - `The query app is pqr but ancestor app is zzz`; `The query namespace is  but ancestor namespace is n1`. Both use
    **project ids**, and the namespace is empty when unset;
  - `Only ancestor queries are allowed inside transactions.`;
  - INTERNAL_ERROR (code 3) `Can't query app zzin a transaction on app pt` (no space, project ids) when the
    transaction belongs to another project;
  - `cursor does not match query`; `The query kind is Z but cursor.postfix_position.key kind is K.`;
  - NEED_INDEX (code 4) with `--require_indexes`: `This query requires a composite index that is not defined. You
    must update ./WEB-INF/datastore-indexes.xml or enable autoGenerate to have it automatically added.` (the
    path/format depends on the index file, see `index-semantics.md`);
  - `count < 0` or `limit < 0` → gRPC UNKNOWN.
- **Quirks** (probe):
  - `limit: 0` → 0 results, `more_results: false`. `count: 0` → 0 results, `more_results: true`, and a handle.
  - `offset: -1` → 0 results, `more_results: true`, and a handle.
  - An explicit `name_space: ""` matches **nothing** (entities stored without a namespace are not found).
  - An incomplete ancestor → 0 results, no error.
  - An empty `compiled_cursor` message, or a garbage `position.start_key`, is ignored.
  - Pseudo-kinds `__kind__`, `__namespace__` and `__property__` work as in v1.
- **Transactions**: the same rules as v1 Datastore mode (ancestor-only, group tracking, snapshot, the `__none__:1`
  pseudo-group). A v3 query never reports `snapshotVersion`; the field does not exist.

### 4.5 Next (`NextRequest` → `QueryResult`)

1. The project comes from `cursor.app`. If that project has never been used → gRPC UNKNOWN.
2. If the handle `cursor.cursor` is not live in that project → BAD_REQUEST `query has expired or is invalid. Please restart it
   with the last cursor to read more results.` This covers an unknown handle, an exhausted query and a reused handle.
3. The next batch:
   - count: the request count, else the original `Query.count`, else 20; at most 300; negative → UNKNOWN;
   - offset: if set, it must equal the query's remaining offset, else BAD_REQUEST `offset mismatch`. Probe: after
     `offset: 400` the first batch skips 300, so Next accepts no offset or `offset: 100`, and rejects 0, 50 and -1.
     Leaving it unset uses the remaining offset;
   - `compile` works per batch even if the query was not compiled (`compiled_cursor` + `result_compiled_cursor`; no
     `compiled_query`).
4. If `more_results`: `result.cursor = request.cursor`, echoed **verbatim** (including `database_id`, and app via
   the mapping). Otherwise the handle is removed.

- The result list is a **snapshot** taken at RunQuery time. Probe: entities put or deleted after RunQuery do not change
  later batches; a deleted entity is still returned. Versions come from the snapshot.
- Handles belong to the project, not the app id: a cursor from an `e~pz` query works as `s~pz`.
- Handles expire after an idle timeout, which is **UNVERIFIED** (not probed).

### 4.6 BeginTransaction (`BeginTransactionRequest` → `Transaction`)

- `app` gives the project.
- `allow_multiple_eg` makes the transaction cross-group (§4.1).
- `mode`: UNKNOWN(0)/READ_WRITE(2) behave as read-write; READ_ONLY(1) rejects writes with `Cannot modify entities in a
  read-only transaction.`
- `previous_transaction`, looked up in this project:
  - with `mode: READ_ONLY` → `specifying a previous transaction handle on a read-only transaction is not allowed`;
  - if it is still live and read-only → `Cannot retry a read-only transaction.`;
  - if it is still live and `allow_multiple_eg` or the mode differs → `Transaction options should be the same as
    specified previous transaction.`;
  - an expired or rolled-back previous handle is accepted (probe).
- `database_id` is ignored and **not echoed**.
- Response: `Transaction{handle, app}`, where `handle` comes from the global handle counter shared with v1 (starts at 1
  and survives `/reset`) and `app` is the request's app id. `mark_changes` and `composite_index` are not set.

### 4.7 Commit (`Transaction` → `CommitResponse`)

- The project comes from `app`. An unknown handle, or one in another project, gives `transaction has expired or is
  invalid`. A handle that was already committed or rolled back gives the same error.
- `mark_changes` and `composite_index[]` are ignored.
- A transaction with no writes returns `cost{index_writes: 0, entity_writes: 0}` and no versions (this includes
  read-only transactions).
- With writes:
  - conflict → code **2 CONCURRENT_TRANSACTION** `too much contention on these datastore entities. please try again.`
    (v1 maps this to ABORTED). The handle stays live, so a later Rollback succeeds;
  - success → `cost` = the summed job cost, and one `version{root_entity_key, version}` **per written key, then per
    deleted key**. Despite its name, `root_entity_key` is the full entity key, not the root; deleted keys that did not
    exist are included. `version` is the commit timestamp.
  - The order is hash-table order, not request order. Probe: groups touched a then b were listed b, a.
    A port should normalize (sort) this order in the harness rather than reproduce it.
  - `commit_time_epoch_micros` is not set.
- The write semantics (one timestamp for the whole commit, a job per tracked group, last write per key wins) are the
  v1 commit path.
- After a successful commit, if `txn_add_task_callback_hostport` is non-empty, each buffered action is sent (§4.11).

### 4.8 Rollback (`Transaction` → empty)

- Success → an empty `Response`.
- An unknown, committed or rolled-back handle → `transaction has expired or is invalid`.
- Rollback after a failed commit succeeds (the handle stays live).

### 4.9 AllocateIds (`AllocateIdsRequest` → `AllocateIdsResponse`)

- If `size` is set:
  - `size > 1000000000` → BAD_REQUEST `cannot get more than 1000000000 keys in a single call`;
  - otherwise `start` = the sequential counter, which advances by `size`, and `end = start + size - 1`.
  - `size <= 0` returns an empty or inverted range, and a negative size **moves the counter backwards** (probe:
    `size: -1` gave `start 20 end 18`, and the next allocation started at 19).
- Else (`max`; 0 when unset): `cur` = the counter. If `cur <= max`, the counter is set to `max + 1`. The response
  is `start = cur`, `end = max(max, cur - 1)`, so a `max` that is already passed gives the empty range `[cur, cur-1]`.
- `model_key` is converted but **not used or validated**: any kind, a complete key, a parent, or no model key at all
  works. `reserve[]` and `trusted` are ignored.
- The counter is the **sequential** one: auto ids for v1 commits and v3 puts come from it. Ids start at 1, and
  `/reset` resets the counter. This differs from v1 `allocateIds`, which returns scattered ids.
- The response has no `cost`.

### 4.10 GetIndices (`GetIndicesRequest` → `CompositeIndices`)

- Only `app_id` is used (to choose the app id in the response); `database_id` is ignored.
- Returns the **global** index list: the index file plus the history-generated indexes of every project
  (`index-semantics.md`). Each is wrapped as `CompositeIndex{app_id: <the request's app id>, id: 0, definition,
  state: READ_WRITE}`.
- Probe: after one composite query in `s~pm`, `GetIndices` for `s~nobody` also returns that index, with
  `app_id: "s~nobody"`.
- If there are no indexes, the response is empty (0-byte envelope).

### 4.11 AddActions (`TaskQueueBulkAddRequest` → empty)

The `TaskQueueAddRequest` fields: the required ones are
`queue_name` = 1 (bytes), `task_name` = 2 (bytes) and `eta_usec` = 3 (int64). The others are: `url` = 4,
`method` = 5, `header` = 6 (group), `body` = 9, `transaction` = 10 (v3 Transaction), `app_id` = 11, `crontimetable`
= 12, `description` = 15, `payload` = 16, `retry_parameters` = 17, `mode` = 18, `tag` = 19, `cron_retry_parameters`
= 20, `datastore_transaction` = 21 (bytes), `dispatch_deadline_usec` = 22. `TaskQueueBulkAddRequest.add_request` = 1.

- If there are no `add_request`s, it succeeds and does nothing.
- The transaction is taken from `add_request[0]`: `datastore_transaction` bytes are parsed as a v3 Transaction (on
  failure: BAD_REQUEST `Invalid transaction`), otherwise `transaction` is used, looked up by its app's project and
  handle:
  - if the project has never been used → UNKNOWN;
  - if the handle is unknown → `transaction has expired or is invalid`.
- Every request is stored with `transaction` and `datastore_transaction` cleared. A transaction holds at most 5
  actions: `Too many messages, maximum allowed: 5` (BAD_REQUEST, checked before adding the batch).
- On a successful **Commit** with a non-empty `txn_add_task_callback_hostport`, each action is sent with a blocking
  call to `CallHandler.HandleCall` on that `host:port` (plaintext gRPC, one connection per hostport). The request is `{service_name: "taskqueue", method: "Add", request: TaskQueueAddRequest with app_id
  mapped back}`. Probe: 5 actions reached a fake server, with request bytes `0a0764656661756c74 1202 7431 187b …`.
  - If the reply carries an `application_error`, a WARNING is logged and the commit still succeeds.
  - A gRPC failure is not caught → gRPC UNKNOWN to the committing client. The data is already committed and the
    handle is gone.
  - If the hostport is empty, the actions are dropped silently.
- Rollback discards the actions.

## 5. Special fields, at a glance

| Field | Behavior |
|---|---|
| Query handles / `Next` | §4.4-4.5: a result snapshot per project; the handle is echoed; it is dropped when exhausted; the counter survives `/reset` |
| `compile` (Query, Next) | §4.4: compiled_query (RunQuery only), compiled_cursor, result_compiled_cursor[], skipped_results_compiled_cursor; bare project ids |
| `count` | The batch size (default 20, max 300); in Next it defaults to the query's `count` |
| `limit` | The total cap; `limit: 0` → empty and finished |
| `offset` | Skipped results (≤300 per batch, the remainder carries over); `skipped_results` is present only if the offset is > 0; Next must send the remaining offset or nothing |
| `failover_ms` (Get, Query) | Ignored |
| `strong` | Get: `false` (without a transaction) means an eventual read. Query: ignored |
| `allow_multiple_eg` | Opts a transaction into cross-group; without it the second group fails (§4.1). The 25-group limit applies (Datastore mode) |
| `mark_changes` (Put/Delete/Transaction) | Ignored |
| `force`, `trusted`, `sequence_number`, `snapshot`, `auto_id_policy`, `composite_index` | Ignored |
| `header` | No such field in these descriptors (`datastore_v3.proto` here has no `header`); unknown fields are skipped |
| `database_id` | `Reference.database_id`: per-key database, stored and visible to v1. `Query.database_id`: ignored (database-blind). `Cursor.database_id`: echoed by Next. `BeginTransactionRequest.database_id`, `GetIndicesRequest.database_id`, `Transaction.database_id`: ignored |
| `allow_deferred` | Ignored (no deferred keys) |
| `read_time_*`, `min_safe_time_seconds`, `safe_replica_name`, `hint`, `require_perfect_plan`, `shallow`, `persist_offset`, `distinct` | Ignored |
| `search_query` | `full-text search unsupported` |
| `__scatter__` | Hidden on read; usable in order/filter; part of the index cost |
| `request_id`, `service_name` | Ignored |

## 6. Mapping onto datastore-oxide

- **Reuse**: put/delete/lookup jobs, versions, group tracking, conflicts, eventual consistency, the query engine
  (`oxide-engine/src/query.rs`), cursors (`cursor.rs`, already v3 CompiledCursor bytes), index files, ids, the
  transaction handle counter and EntityProto encoding (`oxide-api/src/v3.rs`). The v3 handler is a thin layer: the
  app-id mapping, then a lenient protobuf parse, then the engine, then the mapping back.
- **New state**:
  - the app-id cache (process-global, survives `/reset`, not persisted);
  - the per-project query-handle map plus a global handle counter that survives `/reset`, holding snapshot result
    lists and the offset still to skip;
  - per-transaction `allow_multiple_eg` and the action buffer (≤5);
  - the taskqueue callback client.
- **Storage fidelity (the main gap)**: Java stores the v3 EntityProto, so v3 Put → Get round-trips things the v1
  model (`oxide_model::Entity`, a `BTreeMap` of `Value`s) cannot hold:
  - property order;
  - several `multiple: false` values under one name;
  - a name in both `property` and `raw_property`;
  - `owner`, `kind`, `kind_uri`, `meaning_uri`;
  - arbitrary meanings on any value type;
  - multi-field PropertyValues;
  - UserValue;
  - points without a meaning;
  - an `entity_group` that differs from the key root;
  - `computed`/`stashed` handling.

  datastore-oxide stores the v3 `EntityProto` with the entity (`Entity::v3`: app ids replaced by
  project ids, computed properties dropped, stashed ones put back) next to the v1 view Java's
  conversion derives from it (`crates/oxide-api/src/appengine/entity.rs`). v3 reads, exports and
  persistence use the stored proto; v1 reads, queries and write costs use the v1 view. A v1 write
  replaces both. Imports keep the file's proto the same way.
- **Validation layer**: v3 must bypass the v1 checks. Reserved kinds/names/namespaces, empty kinds and long kinds
  must be accepted on Put/Get/Delete, and only the checks listed in §4 apply. A Put/Delete routes all keys to the
  first key's project.
- **Parsing**: generated prost types reject or keep things differently, so mimic the observed lenient parser:
  - skip unknown fields and wrong-wire-type known fields;
  - check required fields recursively and fail with the fixed message;
  - treat any other decode error as `Error parsing protocol message`;
  - for AddActions, use protobuf-java texts, and return UNKNOWN on missing required fields.
- **Ordering to normalize in the harness**: `CommitResponse.version[]`, and the order of trackers/groups.
- **Errors that are bare gRPC UNKNOWN in Java** (§1.4) should be reproduced as UNKNOWN with an empty message (a
  superset that returns a proper error would also be defensible; log it in `docs/superset-backlog.md` per policy).
