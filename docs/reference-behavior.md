# Java emulator reference behavior

Observed from `CloudDatastore.jar` (Cloud SDK `cloud-datastore-emulator`, run under a JRE container).
Anything covered by an automated golden is marked **[golden]**; everything else is still a manual
observation that a later phase should turn into a differential test.

## CLI — [golden] `tests/golden/cli`

Recorded with `tools/record-cli-goldens.sh`; replayed by `crates/oxide-server/tests/cli_golden.rs`.

- All messages (including errors and usage) go to **stdout**; failures exit 1 as `<msg>\nExiting.`
- Options match in order; parsing stops at the first non-matching argument. The last leftover is the
  directory; other leftovers produce `Unexpected option(s): a b.`
- Value options accept only `--name=value` (plus `-p VALUE`); flags accept only `--name`.
  `--testing=true` and `--TESTING` are *not* options (they become the directory argument).
- Values are validated eagerly in argument order. Booleans are case-insensitive (`True` from gcloud).
  Floats follow `Float.parseFloat` (`0.5f`, `NaN`, `Infinity`; not `nan`/`inf`).
- `start` without a directory prints usage (exit 1) unless storage is in-memory
  (`--testing` or `--store_on_disk=false`); `--testing --store_on_disk=true` also needs a directory.
- Directory check: the *parent* must be an existing directory (`Invalid project directory: <parent>`,
  or `null` for a bare relative name).
- Out-of-range port: `Exiting due to exception: java.lang.IllegalArgumentException: port out of range:N`, exit **0**.
- `create` writes only `WEB-INF/index.yaml` = `indexes:\n# AUTOGENERATED\n`; it does not create parents.
- `--project_id` is accepted by `create` (logged as unnecessary), not by `start`.

## Control endpoints — [differential]

Responses carry only `content-length` (no `date`, no `content-type`).

| Request | Response |
|---|---|
| `GET /` (any query) | 200 `Ok\n` |
| `POST /reset` | in-memory: 200 `Resetting...\n`; on disk: 500 `reset failed` (no newline) |
| `POST /persist` | on disk: 200 `Persisting...\n`; in-memory: 500 `The local datastore does not store on disk, persist is not supported.` |
| `POST /shutdown`, `POST /_ah/admin/quit` | 200 `Shutting down...\n`, then the process exits 0 |
| `OPTIONS <any>` | 200, empty |
| anything else (incl. `HEAD /`, `GET /reset`, `/_ah/admin/datastore`) | 404 `Not Found\n` |

**CORS**: every HTTP response (control endpoints, REST, errors; not gRPC) to a request with an
`Origin` header echoes it in `access-control-allow-origin`, adds
`access-control-allow-methods: DELETE,GET,HEAD,PATCH,POST,PUT` and
`access-control-allow-credentials: true`, and echoes `Access-Control-Request-Headers` in
`access-control-allow-headers`. Refused `/reset` and `/persist` (500) get none. Without `Origin`
nothing is added. Checked by `tests/differential/control-endpoints.sh` (header order aside).

**Binding**: `--host=0.0.0.0` listens dual-stack (`[::]`, accepting IPv4 too), as Java's
`ServerSocket` does; rootless podman's port forwarder needs this to connect promptly.

## Datastore v1 data semantics — [golden] `tests/conformance` (REST, replayed by `cargo test`)

Scenarios live in `tests/conformance/scenarios/*.scn`; Java's responses in
`tests/conformance/java/*.golden` (record with `cargo run -p conformance --bin record-conformance --
http://<java-emulator>`). The engine is modeled on App Engine's open-source `LocalDatastoreService`
(Apache-2.0, see `NOTICE`), which the Java emulator is evidently built on.

- **Versions** are per-project commit timestamps starting at 1. Every write job takes the next one; a
  non-transactional commit runs one job per mutation. An unchanged write keeps its old version but
  still consumes a timestamp. Missing entities report the current timestamp. Databases and
  namespaces share their project's counter.
- **Ids**: one global counter (all projects, kinds, namespaces), starting at 1, reset by `/reset`.
  Commit auto-ids use it directly (`--auto_id_policy=SEQUENTIAL`); `allocateIds` always returns
  scattered ids `2^52 + reverse(counter << 13)`. `reserveIds` has no effect.
- **indexUpdates** = App Engine write cost: 1 for a new entity + 2 (asc/desc) per added or removed
  distinct indexed value; 0 for unchanged entities. Arrays contribute each element, an empty array
  one value; embedded entities are flattened to `name.sub` (plus `name.__key__` when keyed). A hidden
  indexed `__scatter__` value (MD5 of the key hash, ~50% of keys) adds 2 for new/deleted entities.
- **Commits**: all mutations are validated first; then they apply in order and an execution error
  (`entity already exists`, `no entity to update`) leaves earlier mutations applied.
  `baseVersion` lower than stored → `conflictDetected` (no write); higher → error; on a missing
  entity any positive base conflicts. No 500-mutation or 1 MiB entity limits.
- **Validation messages** (keys, namespaces, property names, meanings, lengths, geo points,
  project/database ids) are covered by `validation_*`, `meanings*`, `project_ids` and `escaping`.
  Reserved `__*__` kinds/names/namespaces are rejected on writes but allowed on lookups.
- **Unsupported in Java** (rejected as unknown JSON fields): `propertyTransforms`,
  `explainOptions`, `findNearest`, `requestOptions` (each probed on every request that has it:
  `Payload isn't valid for request.`). REST requests are parsed against googleapis without those
  fields, plus the `HAS_PARENT` operator (12, accepted by name and by number), so the accepted JSON
  matches (`rest::java_schema`); gRPC accepts the newer fields. Java also accepts a few unpublished
  fields that oxide rejects as unknown.

## Queries — [golden] `query_*` scenarios

Ported from App Engine's `LocalDatastoreService.runQuery` and its comparators (Apache-2.0, see
`NOTICE`); the v1-layer rules come from recordings.

- **Order of values**: null (and empty arrays) < integers and timestamps (as micros) < booleans <
  strings and blobs (as bytes) < doubles (NaN last) < geo points < keys. Inequalities are ranges
  over that order, so `age > 26` also matches strings. Embedded entities are only indexed through
  their dotted sub-properties (`v.x`, `v.__key__`).
- **Evaluation**: equality values must all be present; some value must fall in the inequality range;
  filtered, ordered, projected and distinct properties must have an indexed value. Multi-valued
  properties sort by min (asc) / max (desc) of the in-range values. Without orders the first
  inequality property sorts first; projected/distinct properties then sort by name; ties break by
  key ascending.
- **Projections** return index values with `meaning: 18` (timestamps as integers, blobs as strings),
  one row per combination of values, no versions. `distinctOn` drops consecutive duplicates.
- **Batches**: at most 300 results (or 300 skipped results); `moreResults` is `NOT_FINISHED` until
  the end and then always `MORE_RESULTS_AFTER_LIMIT` (never `NO_MORE_RESULTS`). Offsets add
  `skippedResults`/`skippedCursor`. Ancestor queries report `snapshotVersion`.
- **Cursors** are v3 `CompiledCursor` protos, byte-identical to Java's (`oxide-engine/src/cursor.rs`).
  Start cursors are exclusive, end cursors inclusive; reusing a cursor in the opposite sort
  direction makes it inclusive (`before_ascending`).
- **Unsupported in Java's Datastore mode**: `OR` (`unsupported composite property operator`),
  multi-value `IN` (`Filter has N properties, expected 1`), `NOT_IN`, and `!=` (bare 500).
- **GQL** ([golden] `query_gql`, `query_gql_aggregate`): `crates/oxide-api/src/gql.rs` parses GQL
  with Java's error messages for the common cases (`Encountered … Was expecting …`, lexical errors,
  `Disallowed literal`). Literals need `allowLiterals`; the parsed query is echoed in the response.
  **Known gap:** aggregation syntax (a leading `AGGREGATE`, `COUNT(*)`/`SUM`/`AVG`/`COUNT_UP_TO`
  projections, `GROUP BY`) cannot run through `runQuery` in either emulator, but the errors differ:
  Java parses it and answers a bare 500 or a 400 from its aggregation grammar, while oxide answers
  its own 400 (and accepts `aggregate`/`over` as property names, which Java rejects as keywords).
  These steps are allowlisted (`tests/conformance/allowlist*.txt`).
- **Databases** ([golden] `databases`): lookups are per database, but queries ignore the database:
  every query (including pseudo-kinds, whose keys then name no database) sees all databases of
  the project, and `__key__` comparisons ignore it, so equal paths in different databases tie and
  keep creation order (re-creating an entity moves it to the end).
- **Pseudo-kinds** `__kind__`, `__property__` (`property_representation`), `__namespace__` (id 1 =
  default namespace); `__entity_group__` queries fail, and looking up `<root>/__entity_group__:1`
  returns `__version__` = group write count + emulator start time in micros.

## Transactions and eventual consistency — [golden] `txn_*`, `consistency*`

Ported from App Engine's `LocalDatastoreService` job model (Apache-2.0, see `NOTICE`), adjusted to
the emulator's fork where recordings differ.

- **Handles** are v3 `Transaction` protos (`0x11` + little-endian handle) from one counter that
  survives `/reset` (the harness normalizes them). Bad bytes → `Invalid transaction.`; empty →
  `a transaction cannot be the empty string.`; unknown/finished → `transaction has expired or is
  invalid`; after a failed commit → `transaction closed` (rollback still succeeds).
- **Conflicts** are per entity group: a transaction records a group's version when it first touches
  it (lookup, ancestor query or write); touching another group or committing with a moved version
  fails with ABORTED `too much contention on these datastore entities. please try again.`. A
  transaction without writes never conflicts. At most 25 groups (`operating on too many entity groups
  in a single transaction.`). Non-ancestor queries are rejected inside transactions.
- **Reads** inside a transaction see the group as of the first outside write after it was tracked
  (lazy snapshot), never the transaction's own writes.
- **Commits** take one timestamp for every write; each tracked group (even read-only ones) gets a job
  and a version bump. Last write per key wins. `commitVersion` (Java-only field) is the highest
  mutation version.
- **Eventual consistency**: each write is a job on its group; each apply attempt draws
  `java.util.Random(seed).nextInt(10000) >= (int)(pct*100f)` (bit-exact). Jobs apply in order; strong
  lookups and strong/transactional ancestor queries roll a group forward; every lookup key and query
  then grooms all pending groups once. Global queries and `EVENTUAL` reads see applied state only.
- **Queries in transactions** (both modes) also track the pseudo-group `__none__:1` (observed
  through `snapshotVersion`, which is the live last commit timestamp), so two writing transactions that both ran a query conflict
  even on disjoint data ([golden] `txn_queries`). Transactional queries report `snapshotVersion`.
- **`HAS_PARENT`** (an operator only in Java's protos): direct children of a key (or, with null,
  root entities), reported like an ancestor query ([golden] `query_parent`).
- **EmulatorConfig** (`GET`/`PATCH /v1/config`, gRPC): an update stores any probability policy it
  carries, then installs forced strong consistency if the request asks for it and otherwise the
  stored probability policy (even for an id-only update); job policy (`probabilityJobPolicy` seed +
  percentage, or `forceStrongConsistency`) and id policy; settings survive `/reset`. Commits under
  the SCATTERED policy use their own id counter and no `__scatter__` property.

## Firestore-in-Datastore mode — [golden] `tests/conformance/java-firestore` (every scenario), `projects/entity_groups_off*`

Spec: `docs/porting-notes/firestore-mode.md`. The mode changes only three things in Java; transactions
keep the optimistic per-entity-group model, and OR / IN / NOT_IN / `!=` / multiple inequalities are
rejected exactly as in Datastore mode.

- **No 25-entity-group limit** in transactions.
- **Non-ancestor queries are allowed in transactions**: they read live data (not the transaction's
  snapshot) and track the group of every matching entity before limit, offset and cursors (not
  phantoms), plus `__none__:1`.
- **Forced strong consistency**: the emulator starts with it (`--consistency` is stored but ignored),
  `GET`/`PATCH /v1/config` always report it, yet a PATCH without `forceStrongConsistency: true`
  installs the stored probability policy. `__entity_group__` is an ordinary (empty) kind; the
  pseudo-kinds `__collection__` and `__document__` (which need a `HAS_PARENT` filter) list the
  collections under a parent and the documents of a collection, across all namespaces.
- **`--enable_entity_groups=false`** (both modes; default true): lookups, deletes, ancestor queries
  and Firestore query tracking use the full key path as the group, puts the root entity, so an
  outside put of an entity a transaction read does not conflict (a lost update) while a delete does.

## REST transport — [golden] `rest_routing`, `escaping`

- Routing follows the `google.api.http` rules: `POST /v1/projects/{p}:lookup` etc. `v1beta3` paths are
  served too. Wrong method on a known path → 404 `Not Found\n`.
- Request JSON that fails to parse (unknown fields, bad enum, overflow, trailing commas) →
  `Payload isn't valid for request.`; an empty body is an empty message. Query parameters other
  than system ones (`alt`, …) are rejected for `body: "*"` methods.
- Request bodies are read only for `content-type: application/json` (JSON) or
  `application/x-protobuf` (binary proto). Other content types → 404 `Not Found\n`.
- Success: 200, `content-type: application/json`, **pretty-printed** JSON (2-space indent;
  an empty message is `{\n}`).
- Errors: compact JSON
  `{"error":{"code":400,"message":"...","status":"INVALID_ARGUMENT"}}`, HTTP status from the code.
  Messages escape `/` as `\/`; both success and error bodies escape U+2028/U+2029 and control
  characters but keep other non-ASCII text. An empty message is omitted (`{"error":{"code":500,"status":"UNKNOWN"}}`).
  Example: lookup of `{"path":[{"kind":"K"}]}` → `Key path element must not be incomplete: [K: ]`.
  `runQuery` with `{}` → `one of fields Query.query and Query.gql_query must be set`.
- Unknown API version (`/v2/...`) → 404 `Not Found (Unsupported API version "v2")\n`;
  `/v1beta1/...` → plain 404.
- Emulator config service: `GET /v1/config` returns `jobPolicy.probabilityJobPolicy.randomSeed`
  and `idAllocationPolicy.policy` (`SEQUENTIAL`); `PATCH /v1/config` with body `config` updates it.
- **Admin index CRUD is UNIMPLEMENTED in Java**: `GET`/`POST /v1/projects/{p}/indexes` →
  501 `Method google.datastore.admin.v1.DatastoreAdmin/ListIndexes is unimplemented`.

## gRPC

- Served over HTTP/2 cleartext on the same port. HTTP/2 requests without a gRPC content type get
  415 with `grpc-status: 13` (`Content-Type is missing from the request`).
- Services: `google.datastore.v1.Datastore`, `google.datastore.v1beta3.Datastore`,
  `google.datastore.admin.v1.DatastoreAdmin`, `google.datastore.emulator.config.v1.EmulatorConfig`,
  `apphosting.tools.devappserver2.CallHandler` (App Engine v3 API server), and server reflection.

## Persistence — [golden] `tests/conformance/projects/persist_*`; durability in `tests/persistence.rs`

Ported from `LocalDatastoreService.load`/`persist` (Apache-2.0, see `NOTICE`), with the emulator's
observed save points.

- Stores on disk unless `--store_on_disk=false` or `--testing`: `<dir>/WEB-INF/appengine-generated/`
  (Java: `local_db.bin`, ours: `oxide_db.bin`), or the `--storage_file` path, which must be an
  existing file or have an existing parent (`<absolute path> is not a valid storage file.`, checked
  before `--index_file`). The default storage directory is created at startup; the file on the
  first save.
- **Saved**: both id counters and every *applied* entity with its version, in creation order.
  **Not saved**: commit timestamps (the first commit after a restart is version 2 again, while
  loaded entities keep their versions), entity groups, unapplied jobs, transactions (old handles →
  `transaction has expired or is invalid`), query history and emulator config.
- **When**: only if a write was applied since the last save (`dirty`; allocating ids alone does not
  count, so ids allocated without a later write are handed out again after a restart): every 30 s,
  on `POST /persist` (`Persisting...`), and at shutdown after rolling every unapplied job forward.
- `/reset` is refused while storing on disk (`reset failed`).

## Admin v1 export / import — [golden] `tests/conformance/projects/{export,import}_*`; interop: `tests/differential/export-interop.sh`

Spec and probe evidence: `docs/porting-notes/export-format.md`.

- **Export** (`POST /v1/projects/{p}:export`) is synchronous and returns a done operation without a
  name; `response.outputUrl` is the absolute prefix (not the metadata file). The prefix is a local
  path (`gs://`, `file://` are just relative paths); an existing path → 400 `The output_url_prefix:
  <raw> already exists`; an unwritable one → 500 `Failed to export entities.`.
- **Files**: `<prefix>/<UTC yyyy-MM-ddTHH:mm:ss_SSS>/` holds the `.overall_export_metadata` LevelDB
  log, and per entity set `<ns>/<kind>/<ns>_<kind>.export_metadata` (a `Backup` proto) plus
  `output-N` LevelDB logs of v3 `EntityProto`s (byte-identical to Java's apart from property order,
  see Known gaps). Entities come out in Java's kind hash-table order, then creation order; every
  database of the project is included.
- **Filters** build entity sets namespace-major; each set is written to a new directory holding all
  sets so far (only the last is complete); empty sets get no files.
- **Side effect** (as in Java): exporting strips `__scatter__` and the embedded-entity index data
  from stored entities, so queries on embedded sub-properties stop matching them and rewriting one
  unchanged counts as a change, until it is rewritten.
- **Import** (`:import`) reads the `.overall_export_metadata` file itself, returns a done operation
  named `projects/<p>/operations/<random>` with an `Empty` response, and writes through the normal
  job/version machinery (one job per entity group, batches of 5000). Keys and *indexed* key values
  take the target project; unchanged entities keep their versions; ids are not reserved. Its filter
  must name whole sets present in the export (`The requested kinds/namespaces are not available`).
- There is no Operations service (404 over REST); the index methods are UNIMPLEMENTED (501).

## Composite indexes — [golden] `tests/conformance/projects/index_*`

Ported from App Engine's `LocalCompositeIndexManager` / `CompositeIndexManager` (Apache-2.0, see
`NOTICE`) plus the emulator's changes; details and evidence in
`docs/porting-notes/index-semantics.md`. Project cases run each emulator in its own directory
(`record-projects` records Java in a container; `tests/projects.rs` replays them).

- **Format**: YAML (`WEB-INF/index.yaml`, or `--index_file` ending in `.yaml`) when storing on disk
  (or storing index configuration with an `--index_file`) and neither `WEB-INF/datastore-indexes.xml`
  nor `WEB-INF/appengine-generated/datastore-indexes-auto.xml` exists; otherwise XML (manual
  `WEB-INF/datastore-indexes.xml`, generated `…/appengine-generated/datastore-indexes-auto.xml`).
  A missing `--index_file` is created as `indexes:\n# AUTOGENERATED\n`; an invalid one exits with
  `<absolute path> is not a valid index yaml.`.
- **History**: every valid `runQuery` (GQL, transactional, pseudo-kind, each page) is recorded,
  keyed by the whole normalized query (filter values, limit, offset and cursors included; the
  transaction, natively served `__key__` filters and a trailing `__key__` ascending order are not).
  History is one per process (all projects and namespaces) and `/reset` clears it.
- **Writes**: each *new* key rewrites the generated section (even if no index is needed): history
  indexes in first-seen order with summed counts, minus manual ones. `--regenerate_indexes` defaults
  to **true**; with `false`, generated indexes already in the file are kept (XML count 0). XML has
  a timestamp comment and `Used N time(s)` counts; YAML has neither. Nothing is written with
  `--store_index_configuration_on_disk=false` (or `--testing`).
- **Missing indexes**: FAILED_PRECONDITION (HTTP 400) `This query requires a composite index that is
  not defined. You must update <index file> or enable autoGenerate|add "# AUTOGENERATED" to have it
  automatically added.`, plus `The minimum required index is:` when existing indexes partly cover
  the query. With `--require_indexes` every run is checked; when the file disables
  auto-generation (`autoGenerate="false"`, or no `# AUTOGENERATED` line) only a key's first run is.
  The checked index set is loaded once per process.
- **Malformed** index files make queries fail with a bare 500.
- **Aggregations** are not implemented by Java (501), see `docs/superset-backlog.md`.

## App Engine v3 API server — [golden] `v3_*` scenarios (both modes), `projects/v3_*`; `tests/appengine.rs`

Spec and probe evidence: `docs/porting-notes/appengine-v3.md`. gRPC
`apphosting.tools.devappserver2.CallHandler/HandleCall` on the shared port; `V3`/`V3HEX` steps in the
conformance harness send it text-format or raw requests (`tools/conformance/src/v3.rs`).

- **Envelope**: only `method` (case-sensitive) and `request` matter (`service_name` and `request_id`
  are ignored). Methods: Get, Put, Delete, RunQuery, Next, BeginTransaction, Commit, Rollback,
  AllocateIds, GetIndices, AddActions; anything else → `application_error{1, "Cannot find
  definition for method: X"}`. Requests parse like proto1: unknown and wrongly typed fields are
  skipped, malformed input → `rpc_error{2, "Error parsing protocol message"}`, a missing required
  field anywhere → `rpc_error{2, "Message was missing required fields.  (Lite runtime …)"}`.
  Engine errors are `application_error`s with v3 codes (BAD_REQUEST 1, CONCURRENT_TRANSACTION 2 for
  contention, INTERNAL_ERROR 3, NEED_INDEX 4); Java's uncaught exceptions are a bare gRPC UNKNOWN.
  Responses are encoded in field-number order, byte-identical to Java's.
- **App ids**: `s~`, `e~`, `dev~` prefixes are stripped; invalid ids are scrubbed
  (`S~Foo` → `scrubbed--oo`). Responses map project ids back to the last app id seen for them, a
  memory that survives `/reset`; compiled cursors and compiled queries carry bare project ids. v1 and
  v3 share all data, ids, commit timestamps, transaction handles and the index history.
- **Lax writes**: no v1 validation (reserved or empty kinds and names, any namespace or database
  id); Put and Delete route every key to the first key's project; incomplete keys take sequential
  ids; the stored `EntityProto` (owner, kind, property order, meanings, user and point values,
  `entity_group` as sent, …) is what v3 reads return, users get an obfuscated id derived from their
  email, and v1 reads see Java's v1 view of it (repeated names become arrays, users become
  meaning-20 entities, points without a meaning get meaning 23). Non-transactional writes run one
  job per entity group and report a version per key (deletes of missing keys take a timestamp too);
  transactional ones buffer immediately (`cost {}`).
- **Queries**: a snapshot taken by RunQuery and handed out in batches (default 20, at most 300; offset
  skipping at most 300 per batch, `Next` must send the remaining offset or none); `more_results` is
  false on the last batch; handles come from a counter that survives `/reset`. Results carry the
  composite index the query needs; `compile` adds compiled cursors and a compiled query.
- **Transactions**: without `allow_multiple_eg` a second entity group fails with Java's
  `cross-group transaction need to be explicitly specified, …found both Element {…} and Element {…}`;
  Commit returns a version per written and deleted key; a failed commit can still be rolled back.
- **AllocateIds** draws ranges from the sequential counter (a negative size moves it back);
  **GetIndices** lists every index of every project (manual ones, plus generated ones unless the file
  disables auto-generation). **AddActions** buffers up to 5 taskqueue `Add` requests per transaction;
  Commit delivers them to `txn_add_task_callback_hostport` as CallHandler calls.

Engine-wide findings from this phase (they apply to v1 too): entity groups ignore the namespace and
database (`K:a` is one group in every namespace of a project); write costs count one row per
composite-index row (manual and history-generated indexes; indexes on `__key__` hold none); the
hidden `__scatter__` property can be filtered and ordered on; a start or end cursor whose index
values do not match the query's orders fails with `cursor does not match query`; a user value is one
indexed value.

## Deliberate divergences

| Area | Java | datastore-oxide | Why |
|---|---|---|---|
| Storage file | `WEB-INF/appengine-generated/local_db.bin` (Java serialization) | `…/oxide_db.bin` (protobuf, written atomically) | Different format; data moves via Admin export/import |
| Admin paths | Written as root in the container (an empty prefix writes at `/`) | The process's permissions apply | Environment, not behavior |
| Unreadable storage file at startup | Logged; starts empty and later overwrites the file | Logged; moved to `<file>.unreadable-<time>`, then starts empty | Never destroy data we cannot read (e.g. a Java `local_db.bin` passed as `--storage_file`) |
| `license` action | Prints the jar's third-party licenses | Prints this project's license | Different dependencies |
| Logging | `java.util.logging` format on stderr | `tracing` format on stderr (`OXIDE_LOG` filter) | stderr is not a contract |
| `localhost` binding | One resolved address | Every resolved address (IPv4 and IPv6) | Clients that prefer `::1` can connect |
| Non-gRPC requests over HTTP/2 | 415 | Served like HTTP/1.1 | Strict superset |
| Entity property order in JSON | Java `HashMap` iteration order | Sorted by name | Proto maps are unordered; the harness sorts both |
| Body `projectId` conflicting with the URL | Request never answered | URL wins | Java bug |
| REST `v1beta3` | Served | 404 | v1beta3 is out of scope |
| `--port=0` banner | Prints `:0` | Prints the port actually bound | `:0` is unusable; lets tests pick a free port |

## Known gaps

Differences not (yet) worth the cost of matching; scenarios avoid them.

| Area | Java | datastore-oxide |
|---|---|---|
| Cursor index values for multi-property sorts | In the entity's stored property order (the order of the write request) | In sort order (prost decodes property maps without order) |
| Property order inside exported `EntityProto`s | The order of the write request | Sorted by name (same cause; Java's import does not care) |
| Malformed `.export_metadata` on import | protobuf-java's exact parse error message | A fixed `Protocol message tag had invalid wire type.` |
